# GuideUI 이슈 PR 절차

CLAUDE.md의 "작업 흐름" 요약을 실제로 실행할 때 쓰는 상세 절차. 사용자는 git/터미널에 아직 익숙하지 않으니, 각 단계에서 실행할 명령과 그 명령이 하는 일을 짧게 설명하고 진행한다.

## 0. 시작 전 확인
- `git status`로 커밋 안 된 변경이 있는지 먼저 확인한다. 있으면 무엇인지 사용자에게 확인 없이 지우거나 덮어쓰지 않는다.
- 다룰 이슈가 GitHub에 없으면(예: 작업 중 발견한 버그) 먼저 `gh issue create`로 이슈를 만들고 번호를 받는다. CLAUDE.md 작업 흐름 규칙("이슈 1개 = 브랜치 1개 = PR 1개")을 지키기 위함.

## 1. 브랜치 시작
```
git switch main && git pull
git switch -c <종류>/<이슈번호>-<설명>
```
- 종류: `feat`, `refactor`, `chore`, `test`, `docs`, `fix` 중 하나.
- 파일 이동과 코드 수정을 한 PR에 섞지 않는다. 섞일 상황이면 브랜치/PR을 나눈다 (예: PR #77 이동 → PR #78 버그 수정).

## 2. 구현 중 검증
커밋하기 전에 항상:
```
npx tsc --noEmit
npm run build
npm run tokens:check   # app/globals.css나 tokens 관련 파일을 건드렸을 때만
```
- `npm run build`(또는 `npm run dev`)를 실행하면 `next-env.d.ts`가 자동으로 재생성된다. 커밋 대상이 아니므로 커밋 전에 항상 `git checkout -- next-env.d.ts`로 되돌린다.
- 이미 알려진 기존 결함(예: 지금은 없는 별도 이슈의 타입 에러)까지 새로 다 고치려 하지 말고, 이번 이슈 범위만 고친다. 범위 밖 발견 사항은 새 이슈로 분리해서 보고한다.
- **화면(UI)이 바뀌는 작업이면 커밋 전에 브라우저로 직접 확인한다**: `npm run dev` 띄우고 claude-in-chrome으로 영향받는 라우트 전부 스크린샷. 특히 리사이즈/드래그처럼 정적 스크린샷만으로 안 잡히는 상호작용은 실제로 조작해서 확인한다.

## 3. 커밋
- 성격이 다른 변경(예: 문서 갱신 vs 실제 코드 수정, 데이터 추출 vs 컴포넌트 분리)은 같은 브랜치 안에서도 커밋을 나눈다.
- 커밋 메시지: `종류: 한국어로 간단한 설명`. 본문에 "왜"가 비직관적이면 짧게 덧붙인다.

## 4. PR 생성
```
git push -u origin <브랜치>
gh pr create --title "..." --body "..."
```
- PR 본문 첫 줄: 이슈 작업을 이 PR에서 다 끝내면 `Closes #번호`, 일부만 끝내면 `Refs #번호`.
- 본문에는 무엇을 왜 바꿨는지, 확인 항목(tsc/build/브라우저 확인 등)을 체크리스트로 남긴다.
- PR 생성 후 사용자에게: "Vercel 프리뷰 확인되면 알려줘"라고 안내하고 기다린다. **사용자 확인 전에 먼저 머지하지 않는다.**

## 5. 머지
사용자가 "머지해줘"/"진행해줘" 등으로 확인하면:
```
gh pr merge <PR번호> --squash --delete-branch
```
- `gh pr merge`가 로컬을 자동으로 `main`으로 옮기고 fast-forward하는 경우가 많다. 그래도 확인:
```
git branch --show-current   # main인지
git status                  # clean인지
git fetch --prune           # 원격에서 지워진 브랜치 참조 정리
```
- 로컬에 브랜치가 남아있으면 지운다. **squash 머지는 git이 "머지 안 됨"으로 인식해서 `git branch -d`가 항상 실패한다** — 원격이 이미 삭제됐고 이슈가 닫혔는지 확인했다면 `git branch -D <브랜치>`로 지운다 (`-d` 아님).
- 마지막으로 `npx tsc --noEmit` 한 번 더 돌려서 main이 깨끗한지 확인하고, `gh issue view <번호>`로 이슈가 닫혔는지 확인한다.

## 6. 이슈 완료 확인 (자동으로 안 닫히는 경우 놓치지 않기)
PR 본문에 `Closes #번호`가 있으면 머지 시점에 GitHub이 알아서 이슈를 닫아준다 — 이건 확인만 하면 된다:
```
gh issue view <번호> --json state
```
아래 경우는 **자동으로 안 닫히니 직접 확인하고 닫는다**:
- 이번 작업이 이슈를 완료시켰는데 PR을 안 만들었을 때(예: 이미 다 되어 있던 걸 검증만 한 경우) → `gh issue close <번호> --comment "왜 완료로 보는지"`.
- PR 본문에 `Refs #번호`만 썼는데, 알고 보니 그게 그 이슈의 마지막 남은 작업이었을 때 → 본문을 `Closes`로 고치거나(머지 전이면), 머지 후라면 `gh issue close`로 직접 닫는다.
- 이슈에 체크리스트가 있고 이번에 일부만 끝났을 때 → 이슈를 닫지 말고 `gh issue edit`으로 체크박스만 갱신한다 (`- [ ]` → `- [x]`).
- 마일스톤 전체가 다 끝나도 마일스톤 자체는 자동으로 안 닫힌다. 마일스톤 안 이슈가 전부 닫혔으면 사용자에게 알리고, 닫아도 될지 확인 후 `gh api -X PATCH repos/{owner}/{repo}/milestones/{번호} -f state=closed`로 닫는다.

작업 하나를 끝낼 때마다: "이번 일이 마일스톤 이슈랑 관련 있었나? 관련 있으면 그 이슈가 지금 실제로 닫혀 있어야 하는 상태인가?"를 스스로 점검한다.

## 사용자가 직접 GitHub 웹에서 머지하는 경우
"내가 브라우저에서 머지할게" 같은 요청이면, Squash and merge를 선택하고 Delete branch까지 눌러달라고 안내한다. 완료됐다고 하면 위 5번의 로컬 정리 단계(`git switch main && git pull`, `git fetch --prune`, 필요하면 `git branch -D`)부터 이어서 진행한다.

## 곁다리로 발견한 버그
작업 중 원래 이슈와 무관한 버그를 발견하면(예: #8 작업 중 발견한 import 경로 깨짐, #9 작업 중 발견한 리사이즈 패널 px/% 문제):
- 그 자리에서 조용히 고치지 말고, 사용자에게 뭘 발견했는지 설명한다.
- 범위가 크면(새 이슈가 필요할 정도면) `gh issue create`로 새 이슈를 만들지, 지금 진행 중인 이슈에 묶을지 물어본다.
- 작으면(현재 PR의 정상 동작을 위해 반드시 같이 고쳐야 하면) 같은 PR에 포함하되 커밋은 분리하고 PR 설명에 "왜 같이 고쳤는지" 남긴다.
